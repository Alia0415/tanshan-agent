## 1. 背景与产品目标

### 1.1 用户问题

用户经常提出“如何评价中山大学”“这个专业怎么样”等宽泛问题。问题相同，背后的目的却不同：有人准备本科报考，有人考虑考研，有人只想了解校园生活。

如果系统直接生成综合介绍，容易出现三个问题：回答覆盖面很广但不解决当前需求；用户不知道还应该补充哪些条件；用户需要反复改写问题才能得到相关信息。

团队观察到现有使用体验中缺少主动澄清。本产品不将该观察扩展为对知乎“看山”当前全部能力的事实判断。

### 1.2 产品定义

问山通过少量、可跳过的交互式追问，帮助用户明确问题的使用目的和关键条件，然后结合知乎社区内容生成有来源、贴合当前需求的回答。

核心价值：降低提问门槛，提高回答与用户需求的相关性，让用户能看见、修正系统对自己问题的理解。

### 1.3 MVP 要达成的结果

1. 用户输入宽泛大学问题后，可通过最多两轮澄清进入回答。
2. 对已经明确的问题，系统可以直接检索回答，不强制填写背景。
3. 同一原始问题在不同已确认条件下，检索重点和回答结构产生可解释的差异。
4. 最终答案展示真实返回的来源，并明确资料不足之处。
5. 完整流程能在公网 Demo 中操作；失败状态有明确出口。

## 2. 用户与首发场景

| 用户 | 典型问题 | 主要需求 | 必须避免 |
| --- | --- | --- | --- |
| 准备本科报考的学生 | 如何评价中山大学？ | 专业学习、就业、学校体验 | 一上来就要求填写完整个人资料 |
| 考虑考研的学生 | 中大适合读研吗？ | 专业方向、科研或就业取向 | 继续追问高考省份等无关条件 |

第一版重点支持单所大学的评价、学习体验、就业体验和择校信息了解。不承诺录取概率预测、志愿填报决策或专业数据库全覆盖。

非大学类问题提供通用直接问答入口；若 API 无法完成，明确告知。第一版不宣称所有领域都具备同等质量的动态追问。

## 4. 用户流程与页面

### 4.1 主流程

`首页提问 → 理解问题 → 必要时澄清 → 确认聚焦问题 → 检索 → 生成回答 → 查看来源／修改条件`

分支约束：

- 问题已明确：跳过澄清和手动确认，展示理解摘要后直接检索。
- 用户选择“直接回答”：立即停止补问，按已有条件执行；不再弹出强制确认。
- 选择“整体了解”：视为有效目的，不继续要求补专业、地区等条件。
- 用户修改条件：旧答案保留并标为“基于此前条件”，新请求只使用最新确认信息。

### 4.2 首页

页面元素：产品名、简短介绍、问题输入框、发送按钮、三个示例问题。

推荐文案：“先说说你想知道什么，我们一起把问题问清楚。”

示例问题：

- 如何评价中山大学？
- 想了解一所大学的计算机专业，应该关注什么？
- 中山大学的校园生活怎么样？

输入约束：去除首尾空白；为空不可发送；最多 2,000 字符，超出时保留输入并提示缩短。发送过程中防止重复提交。示例点击后填入输入框，由用户发送。

### 4.3 澄清卡片

卡片出现在对话中，包含一句说明、问题、选项和自由补充入口。

- 单选项选中后显示选中状态，由“继续”统一提交。
- 补充卡片可包含最多两个字段；关注点多选最多两项。
- 没有做出选择时，仍可使用“跳过，直接回答”。
- 自由输入与选项具有同等地位；无法解析的补充不能静默丢弃。
- 提交后保留已选内容，提供“修改条件”入口。
- 当多选达到上限时，说明“最多选择两项，帮助答案更聚焦”。

### 4.4 问题确认

展示学校、目的、专业和关注点等已确认标签，以及一句自然语言聚焦问题。

示例：“从本科报考角度，了解中山大学计算机相关专业的学习体验和就业情况。”

支持修改标签及补充文字。自由修改如果与旧条件冲突，以最新明确输入为准；无法确定时指出冲突供用户修改，不替用户猜测。

按钮：“开始分析”“修改条件”。不展示内部模型名、JSON、Prompt 或接口术语。

### 4.5 回答页

顶部保留“本次回答依据的条件”。正文依次展示：

1. 针对当前需求的简短结论。
2. 按用户关注点展开的分析。
3. 来源之间有依据的差异或相反经验；没有分歧证据时不强造对立。
4. 资料不足、需要进一步核对的内容。
5. 可展开的来源列表与“修改条件再问”入口。

来源卡片展示标题、作者、来源类型、返回的发布时间或更新时间（字段可靠时），并可打开原始 URL。未返回时间时不补造时间。

桌面端可将来源放在右侧；移动端放在正文后方折叠展示。来源不可挤占正文阅读宽度。

## 5. 追问策略

### 5.1 是否追问

追问需要同时满足：当前目的存在实质性歧义；缺失信息会改变检索或回答方向；用户没有要求直接回答；未达到轮次上限。

| 输入 | 动作 | 理由 |
| --- | --- | --- |
| 如何评价中山大学？ | 问使用目的 | 本科报考、考研、校园体验的答案不同 |
| 中大计算机本科课程体验怎么样？ | 直接检索 | 对象和关注点足够明确 |
| 我是广东高三学生，想了解中大计算机就业 | 直接检索 | 已给出目的线索、专业和关注点 |
| 中山大学在哪里？ | 直接回答 | 基础事实，无需画像 |
| 先整体介绍一下，不要追问 | 直接检索回答 | 尊重明确交互要求 |
| 那换成考研呢？ | 更新目的 | 保留仍适用信息，移除本科报考专属条件 |

### 5.2 轮次定义与停止条件

一轮指系统展示一张澄清卡片，用户提交一次。自动重渲染不计为新轮次，但不得借此追加无限字段。

- 第 1 轮：只在目的不明确时询问目的。
- 第 2 轮：根据目的，最多询问两个最重要的缺失字段。
- 如果最初目的已经明确，第一张卡片即可询问缺失条件，无需走固定两轮。
- 达到两轮、用户点击直接回答、信息已足够、用户选择整体了解，任一成立即停止澄清。
- 用户主动修改条件不触发重新收集全部信息，也不自动重置追问计数。

### 5.3 大学场景字段

| 字段 | 触发条件 | 示例 | 规则 |
| --- | --- | --- | --- |
| 使用目的 | 原问题过于宽泛 | 本科报考、考研择校、校园生活、整体了解 | 通常优先询问 |
| 意向专业 | 报考或读研且答案依赖专业 | 计算机、医学、经管、自由输入、尚未确定 | 尚未确定也是有效选择 |
| 关注重点 | 目的明确但角度宽泛 | 就业、学习体验、科研、报考难度 | 最多两项，不与已有问题重复 |
| 高考省份／年份 | 明确涉及本科录取或招生信息 | 用户自行提供 | 不默认询问居住地；缺失时不生成精确录取结论 |
| 校区 | 已知体验问题存在校区差异且会影响回答 | 自由输入、不确定 | 未确认时说明差异，不擅自指定 |

两轮内不能收集完全部信息时，优先核心目的与关注点。精确结论依赖但尚缺失的条件应在答案中说明，不延长问卷。

### 5.4 模型与规则的职责

模型：提取明确表达的信息、判断问题是否宽泛、建议追问字段、生成自然语言选项。

后端规则：限制轮次和字段数、校验输出、阻止重复询问、维护用户确认状态、决定跳过与降级路径。

不能仅凭模型推测记录年龄、性别、分数等背景。显式输入可提取为事实，模型推测只能用于建议待确认项。

模型输出解析失败时，大学宽泛问题使用预设目的卡片；问题已明确或无法判定时按原问题直接检索，不把失败变成强制问卷。

## 6. 检索与回答要求

### 6.1 检索策略

- 将对象、专业和关注点组织成默认 1～2 个查询，单次回答最多 3 个查询。
- 每个知乎查询默认取 5 条结果；以实际服务端限制为准。
- 使用内容 ID 或规范化 URL 去重，保留原始返回 URL 用于溯源。
- 关键词应忠于用户条件，不加入未经确认的判断，例如“就业差”“最值得报考”。
- 空结果最多进行一次关键词简化，计入总查询上限。
- 招生计划、录取数据等时效事实优先补充官方来源；可使用全网搜索的站点筛选能力。未找到可靠资料时不输出精确事实。
- 不将搜索排名或赞同数等同于真实性，不将几个回答概括为全部学生的共识。

### 6.2 示例

已确认条件：本科报考、计算机、就业与学习体验。

查询示例：`中山大学 计算机 本科 就业`、`中山大学 计算机 本科 学习体验`。

切换为校园生活后，应检索与宿舍、交通、活动等当前关注点有关的内容。无需为了证明变化而强制更换全部来源；来源相同时，应能解释其与不同关注点的相关性。

### 6.3 回答与引用

- 回答开头必须回应已确认目的，避免用大段学校百科介绍替代需求分析。
- 关键事实和经验归纳关联来源编号，由后端映射到已检索的真实链接。
- 模型返回未知来源编号时不渲染为有效引用，相关内容进入引用校验或降级处理。
- 知乎搜索的 `ContentText` 是摘要，不得声称读取了未获取的全文。
- 个人经验使用“该回答提到”等限定表述，不冒充统计结论。
- 若所有检索均失败或为空，不生成“综合知乎资料可知”等有证据暗示的回答。展示真实状态，可给出明确标注为一般性建议的分析框架。
- 用户条件应作为回答范围，不作为学校事实的证据。

检索内容作为参考材料处理，不执行来源文本中的指令。前端清理 HTML，只渲染安全内容和合法网页链接。

## 7. 状态与接口协议

### 7.1 状态

| 状态 | 用户看到的内容 | 下一步 |
| --- | --- | --- |
| understanding | 正在理解你的问题 | 澄清／确认／直接检索 |
| clarifying | 追问卡片 | 提交、跳过、修改 |
| ready | 聚焦问题与条件 | 开始分析或修改 |
| searching | 正在查找相关知乎内容 | 生成或错误提示 |
| generating | 正在整理与你相关的回答 | 流式正文或分阶段反馈 |
| completed | 完整回答和来源 | 反馈、修改条件 |
| error | 当前失败原因与下一步 | 用户发起重试或修改 |

修改已确认条件时增加 `context_version`。答案、引用与请求必须关联该版本。旧请求即使晚于新请求返回，也不能覆盖新条件对应的内容。

刷新恢复当前会话。刷新时仍在运行的请求应恢复状态或明确提示连接中断，不自动发起另一次收费生成请求。

### 7.2 最小会话结构（应用自定义）

```json
{
  "session_id": "server_generated_id",
  "original_question": "如何评价中山大学",
  "stage": "ready",
  "context_version": 2,
  "clarification_count": 2,
  "confirmed_context": {
    "school": "中山大学",
    "purpose": "undergraduate",
    "major": "计算机",
    "priorities": ["就业", "学习体验"]
  },
  "free_text_context": [],
  "focused_question": "从本科报考角度了解中山大学计算机的就业与学习体验"
}
```

原始补充文字保留在当前会话中，解析失败时仍可供回答使用。可选字段缺失保持未知，不填入默认个人背景。

### 7.3 应用接口（建议契约，非知乎原生接口）

| 接口 | 主要输入 | 主要输出 |
| --- | --- | --- |
| `POST /api/sessions` | `question` | 会话 ID、状态、已知条件、可选澄清卡片 |
| `POST /api/sessions/:id/clarifications` | `context_version`、字段选择、自由补充、`skip` | 更新条件、聚焦问题、下一状态 |
| `PATCH /api/sessions/:id/context` | `context_version`、修改内容 | 新版本、条件摘要、`ready` 状态 |
| `POST /api/sessions/:id/answer` | `context_version`、`request_id` | 当前生成任务或答案流 |
| `GET /api/sessions/:id` | 会话身份 | 当前状态、条件、已有回答与来源 |
| `POST /api/sessions/:id/feedback` | 答案 ID、反馈类型、可选原因 | 接收状态 |

服务端校验选项值、数量和长度；用户可输入自由文字，但不能伪造状态和已追问次数。会话访问同时校验匿名会话凭证，不仅依赖可见会话 ID。

同一 `request_id` 的重复提交返回现有任务或结果，不重复调用生成接口；旧版本提交返回条件已变更提示。

## 8. 技术边界与建议方案

### 8.1 已有文档能够支持的部分

- 知乎搜索 API 提供标题、作者、内容摘要、URL 等字段。
- 知乎直答 HTTP API 接受 `model`、`messages`、`stream`。
- 文档明确列出 `zhida-fast-1p5` 和 `zhida-thinking-1p5` 支持 role、content 上下文传参；实际模型可用性受账号权限影响。
- CLI 的 `answer --query` 面向单轮；应用多轮可通过 HTTP `messages` 或应用维护的上下文摘要实现。

文档未保证严格 JSON Schema、工具调用、追问质量或模型对外部检索材料的引用忠实度。上述效果必须实测，不能把提示词中的要求当成平台保证。

### 8.2 建议实现

- 前后端：一个 TypeScript Web 项目，建议 Next.js；无需拆分微服务。
- 澄清：优先测试 `zhida-fast-1p5`，配合模板与后端校验。
- 内容：应用主动调用知乎搜索，保存本次来源编号映射。
- 回答：优先测试 `zhida-thinking-1p5` 对用户条件和检索材料的遵循情况。
- 会话：单实例持久磁盘部署可用 SQLite；无状态部署使用持久数据库。
- 追问、检索、回答作为三个处理步骤，无需三个独立 Agent。

若知乎直答不能稳定完成澄清，MVP 使用规则模板完成大学场景追问。若最终回答模型无法可靠使用给定来源，需要调整生成方案并重新验收，不能仅靠 UI 包装宣布实现。

### 8.3 凭证与数据

Access Secret 仅保存在服务端环境变量或安全凭证系统。不得进入浏览器、源码仓库、日志或演示画面。

默认匿名会话保留 24 小时用于刷新恢复，到期清理；开始新会话不复用旧个人条件。该保留期是 MVP 建议，页面应有简短说明。

业务会话存储与诊断日志分开：业务存储只保存恢复所需的问题、选择、回答和来源；诊断日志不记录完整用户文本、凭证和完整模型响应。无须将用户输入保存为长期画像。

## 9. 异常、性能和可用性

| 情况 | 用户提示／行为 | 后端要求 |
| --- | --- | --- |
| 澄清格式错误 | 预设卡片或直接回答 | 校验失败不渲染原始 JSON |
| 额度不足／限流 | 当前暂时无法继续，可稍后重试 | 停止循环调用，不伪装空结果 |
| 搜索无结果 | 未找到足够相关资料，可修改条件 | 最多一次简化查询，之后明确降级 |
| 部分查询失败 | 基于已获取资料回答，并提示范围有限 | 保留成功来源，避免捏造缺失部分 |
| 生成超时 | 本次生成未完成，可手动重试 | 不自动重试直答 POST |
| 流式中断 | 保留已显示内容，标记回答未完成 | 不记录为成功答案 |
| 用户连续点击 | 一次加载状态 | 请求去重 |
| 修改条件后旧请求返回 | 继续展示新状态 | 以版本号阻止旧结果覆盖 |

体验目标（待真实测量，不是现有性能承诺）：

- 提交后 300ms 内出现本地加载反馈。
- 澄清结果目标 p95 在 8 秒内；首个可读回答片段目标 p95 在 30 秒内，取决于供应方实际延迟。
- 超过目标时展示阶段提示；设置可配置请求截止时间，首版建议生成最多等待 120 秒。
- 移动端 375px 宽度下没有横向滚动；选项和按钮可触控、可通过键盘操作；选中状态不只靠颜色区分。
- 缓存和去重必须包含查询与必要过滤条件，不能把不同用户条件混用成同一答案。

## 10. 验收用例

| 编号 | 操作 | 通过标准 |
| --- | --- | --- |
| A01 | 输入“如何评价中山大学” | 先问目的，不直接收集年龄和完整地区信息 |
| A02 | 输入明确专业和关注点的问题 | 跳过不必要澄清，检索围绕原始目的 |
| A03 | 选择本科报考→计算机→就业与学习体验 | 确认页准确反映条件，回答按两项关注点组织 |
| A04 | 原问题已包含“广东高三、计算机、就业” | 不重复询问已明确字段 |
| A05 | 任一澄清步骤点击直接回答 | 立即进入检索，不出现新的必填问卷 |
| A06 | 选择整体了解 | 允许直接生成整体回答 |
| A07 | 输入选项之外的自由补充 | 补充被保留并影响问题摘要或回答 |
| A08 | 连续两轮后仍缺少细节 | 停止追问，按已知信息回答并说明限制 |
| A09 | 把本科报考改为考研 | 清理不适用的高考条件，保留仍有效的学校／专业 |
| A10 | 检查答案引用 | 所有引用均可映射到真实检索结果，抽查关键结论有材料支持 |
| A11 | 模拟空结果、限流、无效凭证 | 三种状态分别处理，不伪造来源或回答成功 |
| A12 | 模拟模型 JSON 不合法 | 澄清流程仍能降级继续 |
| A13 | 连续点击生成或刷新页面 | 不产生无意的重复生成请求；可恢复或显示中断状态 |

## 11. 产品效果评估

发布前准备 20 条人工标注案例：6 条宽泛大学问题、6 条明确问题、4 条已包含多个条件的问题、4 条跳过／修改／自由补充案例。

建议门槛：是否追问判断至少 18/20 与标注一致；明确输入的信息不重复问；所有案例遵守轮次上限。标签存在分歧时先讨论标注，不将单一评审偏好当成事实。

另外选取 6 组“同题不同目的”案例，人工比较：问题摘要是否准确，检索是否相关，答案是否回应关注点，引用是否支持结论。追问版与直接回答版尽量保持同等检索预算和模型设置，避免把增加调用量误认为澄清的收益。

线上仅记录必要事件：提交问题、展示澄清、提交选择、跳过、确认、答案成功／失败、来源点击、反馈。事件携带匿名会话标识、轮次和状态，不携带原始问题全文。

观察口径：

- 澄清提交率＝至少提交一次澄清的会话数／展示过澄清的会话数。
- 跳过率＝点击直接回答的会话数／展示过澄清的会话数。
- 回答成功率＝完成回答的任务数／去重后的回答任务数。
- 有帮助比例＝“有帮助”反馈数／全部有效反馈数；同时展示反馈量，不代表所有用户满意度。

优先观察追问是否成为负担，以及答案是否更相关，不以追问次数越多作为成功。
